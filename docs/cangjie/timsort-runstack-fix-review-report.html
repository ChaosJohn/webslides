timSort run 栈容量与合并不变式修复方案

排序库在特定数据下发生 run 栈越界崩溃（issue #250）。本文档说明故障机理、 修复方案与风险评估，供评审会决策参考。文中动画与数据来自按源码逻辑实现的模拟器，生成方法见附录。

关联 issue Cangjie/cangjie_runtime#250 修复 PR #1764（容量公式 · 治标） 修复 PR #1779（不变式补全 · 治本） 涉及 stable_sort.cj / array_list.cj
结论：两个 PR 配套构成完整修复；超大数组场景无实质风险；建议通过

1一页速览

本次评审的修改由两部分组成：一个更准确的容量计算公式（PR #1764）与一条补上的合并触发条件（PR #1779）， 两者缺一不可；另有扩容兜底，共同消除排序库在特定数据下的数组越界崩溃。

问题

对特定分布的数据调用 Array.sort() / ArrayList.sort() 时， 排序内部维护的 run 栈写入越过预分配容量，抛出 IndexOutOfBoundsException（issue #250）。

根因（两个缺陷叠加）

① 容量公式数学错误：系数用了 1.0，理论上需要 1.44（黄金比例）——从 n≥2048 起系统性低估； ② 不变式漏检：合并条件只查栈顶一层，深层违规无人发现，栈深可突破理论值。

方案（两个 PR 配套）

#1764 换用严格上界公式 Int64(log2(size)*1.5)+8；#1779 补上第二个合并不变式检查 （对标 OpenJDK / Python），使公式的前提真正成立。

修复的整体结构（三层防御）

1

#1779 合并不变式整栈维持（治本）

每压入一个 run 都同时检查栈顶两层不变式，违规即合并并逐层下探，保证"栈深 ≤ 1.44×log₂(n)"这一上界的前提成立。

▼ 若上界仍被极端数据突破
2

#1764 容量公式严格上界（治标）

Int64(log2(size)×1.5)+8：对任意 size ≥ 65 恒为栈深的严格上界（n=2⁶³ 时也仅 102），并留有刻意余量。

▼ 若容量仍然不足
3

growRunStack 倍增扩容（兜底）

栈满时按倍增策略扩容，保证任何情况下都不发生越界写，是最后一道防线。

2背景知识

本章介绍四个概念：timSort、run、run 栈、合并不变式，是理解后文缺陷分析与修复方案的基础。

2.1 timSort 是什么

仓颉标准库中 Array<T>.sort() 与 ArrayList<T>.sort() 的底层实现（std/sort/stable_sort.cj、 std/collection/array_list.cj）。它是一种混合式稳定排序：小数组直接用插入排序；大数组先识别数据中 天然有序的段，再把这些段归并起来。Python 的 list.sort（2002 年由 Tim Peters 提出） 与 Java / Android 的 Arrays.sort 使用的是同一算法。本次修复以这两个实现为对照，来源与发展过程见 §8.2。

2.2 run：天然有序段

timSort 扫描数组，把连续升序（或降序，降序段会被原地反转成升序）的元素切成一个 run。 每一个短于 minrun（约 32~64）的 run 都会用二分插入排序补长到恰好 minrun，与它是第几个 run 无关； 仅当数组剩余元素已不足 minrun 时，才把剩余部分整体排为最后一个 run（它可能短于 minrun）。切分完成后，排序就变成： 把所有 run 两两归并成一个有序序列。切分过程见下方动画（可逐步播放或自动播放，本例 minrun = 5）：

2.3 run 栈：排序过程的"待合并队列"

run 产生后按顺序压入一个栈（栈底是数组前段的 run，栈顶是最新识别的 run）。每压入一个 run，就检查栈顶： 若不满足"秩序"，就把相邻的两个 run 归并成一个更长的 run，直到秩序恢复。全部 run 识别完后，栈里剩下的 run 会被最终归并成结果。本次崩溃的"栈"就是这个 run 栈：它的容量在排序开始前预分配，容量不足时， 超过容量的 run 会越界写入。

合并不变式：栈的"秩序"

标准 timSort 要求栈上任意位置满足：

len[i] > len[i+1] + len[i+2]   // 每个 run 严格长于其上方两个 run 之和

即 run 长度从栈底到栈顶呈 Fibonacci 式递减（1, 1, 2, 3, 5, 8, 13…）。这条不变式的作用有二： ① 使合并总是发生在长度相近的 run 之间，避免用长 run 反复合并短 run； ② 给栈深一个对数上界，这是容量公式的数学根基：

Fibonacci 最坏栈型（自栈顶向下）

栈深上界推导

栈深为 d 时，栈内 run 长度之和至少是 Fibonacci 级数之和：

n ≥ F(d+2) − 1

由 Fibonacci 通项 F(d) ≈ φd / √5（φ ≈ 1.618，黄金比例）反解：

d ≤ logφ(n) = log₂(n) / log₂(φ) ≈ 1.44 × log₂(n)

同一推导给出 Python 的最大栈深 85 = logφ(2⁶⁴/32)， OpenJDK 的 40 ≈ logφ(2³¹/32)。

要点：1.44。它是不变式完全维持时栈深的最坏系数。 容量公式必须覆盖 1.44 × log₂(n)，否则上界不成立。

违反"秩序"时，合并哪两个？比较被检查三元组的两端（下方第 3 个 run 与栈顶 run）： 较短一端所在的相邻一对被合并——效果是合并三元组中较短的两个 run，使合并双方长度相近 （栈为 [30, 20, 45] 时，两端 30 与 45 中 30 较短，合并下方一对 30+20）。 若栈内只剩 2 个 run 且下方 run ≤ 上方 run（不满足严格递减），则直接合并这一对、无需选择。

2.4 minrun（mrl）：最短 run 长度

切分时每个 run（除数组末尾最后一个外）都会被补长到至少 minrun（32~64 之间，由数组规模决定）。 旧容量公式依赖"每个 run ≥ mrl"这个事实来收紧估算 —— 而新公式刻意不再依赖它，原因见 §4.4。

3缺陷分析：issue #250 为什么崩溃

3.1 现象

复现路径：构造 Fibonacci 递减 run 分布的数据 → 调用排序 → run 栈超过旧公式分配的 8 个槽位 → IndexOutOfBoundsException（数组越界写）。这是公共 API 的缺陷， 特定数据可稳定触发。

根因是两个独立缺陷的叠加，下面分别说明，各配一个按源码逻辑实现的模拟器动画。

3.2 缺陷一：容量公式数学错误（PR #1764 修复对象）

旧公式（stable_sort.cj / array_list.cj 修改前）：

let stackLen = Int64(log2(Float64(this.size) / Float64(mrl) + 2.0)) + 1

这个 log₂(n/mrl) 的形状隐含假设"run 长度每上一层至少翻倍"（系数 1.0）。 而不变式实际只保证 黄金比例 φ ≈ 1.618 的递减（系数 1.44）：Fibonacci 递减比翻倍递减慢， 同样的元素数能容纳更深的栈，旧公式因此系统性低估最坏栈深：

3.3 缺陷二：合并不变式漏检（PR #1779 修复对象）

§2.3 的不变式要求整栈逐层成立，但旧的合并触发条件只查了栈顶一层：

if (l <= ln + ln1) {   // 只检查 len[n-1] ≤ len[n] + len[n+1]（i = n-1 层）

这对应标准实现两个检查条件中的第一个（OpenJDK mergeCollapse 条件 1）。标准实现还有第二个条件 —— 检查 len[n-2] ≤ len[n-1] + len[n]（i = n-2 层）—— 旧实现从未移植这一条。

旧代码的检查窗口

仅查这 3 个
run（栈顶·刚压入）i = n+1
run（第 2 个）i = n
run（第 3 个）i = n-1
run（第 4 个）i = n-2 ✗ 无人检查
run…
run（栈底）i = 0

更深层永远不在检查窗口内 —— 那里产生的违规无人发现。

新代码的检查窗口（PR #1779）

查 4 个 · 两层
run（栈顶·刚压入）i = n+1
run（第 2 个）i = n
run（第 3 个）i = n-1
run（第 4 个）i = n-2 ✓ 纳入检查
run…
run（栈底）i = 0

每次压栈后若发生合并，窗口会逐层下移继续检查， 直到整栈恢复（见 §5.2）。

漏检的后果：合并会产生一个更长的 run，可能破坏更深一层的 Fibonacci 递减，而旧代码的检查 看不到那一层。深层违规一旦出现就不会再被清除，后续数据可以继续利用这种"扁平化"使栈深超过理论值。 issue #250 的复现数据正是这样越过了旧公式的 8 个槽位。

3.4 两个缺陷的关系

缺陷一（公式）使预分配容量小于理论需要；缺陷二（漏检）使实际栈深可以超过理论值。 两者叠加造成越界，因此修复必须同时包含两个 PR，详见下文。

4修复一：容量公式（PR #1764 · 治标）

4.1 修改内容

stdlib/libs/std/sort/stable_sort.cj · timSort()（Comparable 版与 comparator 版两处同构）
- let stackLen = Int64(log2(Float64(this.size) / Float64(mrl) + 2.0)) + 1
+ let stackLen = Int64(log2(Float64(this.size)) * 3.0 / 2.0) + 8
（PR #1779 将同一公式同步替换至 array_list.cj 的 ArrayList 版 timSort）

4.2 新公式逐项拆解（点击公式中的每一部分）

Int64( … )= log₂( Float64(this.size) ) × 3.0 / 2.0 + 8

4.3 修复前后容量曲线

旧公式 log₂(n/mrl+2)+1 理论最坏栈深 ≈ 1.44·log₂(n)（含 minrun 收紧） 新公式 Int64(1.5·log₂(n))+8

红色曲线沉入橙色曲线下方的区域（n ≥ 2048 起）即"旧公式必然越界"的规模区间； 绿色曲线全程高于橙色曲线，且最小值 17（n=65）、最大值 102（n=2⁶³）。鼠标悬停可查看任意规模的具体数值。

4.4 三个刻意的取舍（评审关注点）

  1. 系数 1.5 而非精确的 1.4404：免去对 log₂(φ) 的浮点精确计算、吸收 log₂ 自身的浮点误差， 并对理论值留约 4% 余量 —— 把"恰好压线"变成"明显富余"。
  2. +8 而非 +1：纯工程余量 —— 防小 size 时截断后容量过小（若未来入口短路条件改动，1.5×log₂ 趋近 0， 无常数项可能算出 0 容量）；吸收 Float64 截断误差，保证结果恒"严格大于"；对标 OpenJDK（len<120 固定给 5） 与 Python（固定 85）的小数组档位。代价仅约 128 字节。
  3. 刻意不除以 mrl（旧公式除了）：除 mrl 可让上界更紧，但依赖"栈底 run ≥ mrl"的前提； 新公式放弃该收益，换来一个对任意 n 无条件成立的简单严格上界。代码注释中已明确写入 do not tighten it into a lower-bound estimate，防止未来维护时把参数当冗余"优化"掉。

随公式固化的推导注释（stable_sort.cj:425-432）

// Run stack capacity: maybeMerge maintains the invariant that each run
// is strictly longer than the two runs above it combined (lengths
// decrease Fibonacci-style from bottom to top), so a stack that never
// triggers a merge is at most ~1.44 * log2(size) deep (1.44 is
// 1/log2(golden ratio)). The 1.5 factor is deliberate headroom over
// 1.44 and the +8 covers constant terms for small sizes, so the
// formula is a strict upper bound on the stack depth; do not tighten
// it into a lower-bound estimate.
要点：新公式的每一项都只放大不缩小（1.5 > 1.44、+8 > 0、截断损失 ≤ 1 由余量覆盖）， 因此对任意 size 都是栈深的严格上界；推导已固化为代码注释，防止后续维护时误改。

4.5 公式每个数字的来源与业界对照

数字来源与作用业界参考
log₂(size) 栈深的唯一驱动变量：来自合并不变式（Fibonacci 递减）推出的对数上界，推导见 §2.3 Python 与 OpenJDK 的容量推导同样以 logφ(n)（= 1.44·log₂n）为根基
× 3.0 / 2.0（= 1.5） 理论系数 1.4404 = 1/log₂(φ) 的向上余量（+4.2%）：免去对 log₂(φ) 的精确浮点计算， 并吸收 log₂ 自身的浮点误差 OpenJDK 按 logφ 分档后取 49（推导值 38 + 余量）—— 同为"推导值 + 取整余量"手法
+ 8 纯工程防御常数，数学上非必需（1.5×log₂(size) 单独已大于已分析场景的真实栈深），四个作用见下 OpenJDK 最小档 len<120 固定给 5、Python 按推导固定 85 —— 业界容量公式普遍是"理论项 + 常数余量"结构
Int64( … ) 浮点转整型截断，最多损失 1 个槽位，被 1.5 与 +8 的余量覆盖 同类实现均对推导值取整后使用

为什么常数是 8？

  • 数学上非必需：对 size ≥ 65，1.5×log₂(size) 单独已大于所有已分析场景的真实栈深 （n=65 → 计算 9 层、实际最多 1~2 层；n=6195 → 计算 18 层、实际最多 11 层）—— 8 不参与上界的成立性。
  • 覆盖已识别的全部误差项（合计 ≤ 3）：① Int64 截断 ≤ 1；② Float64 舍入 ≤ 1（size > 2⁵³ 时）； ③ 小尺寸防御下限 —— 若未来入口短路条件改动，极小 size 会令 1.5×log₂ 趋近 0，无常数项将得到 0 容量。 取 8 约为三项合计的 2.5 倍冗余。
  • 保证"严格大于"：使结果恒严格高于理论栈深，而非在极端取整下"恰好等于"。
  • 成本：极端规模下多占 8 槽 × 2 数组 × 8B = 128 字节，排序结束即释放。
  • 评审可选：若希望最小化，+3 即可恰好覆盖上述三项误差（+4 留 1 余量、再省 64B）， 但无实际收益，且降低对未来入口改动的防御。

5修复二：合并不变式补全（PR #1779 · 治本）

5.1 修改内容

在合并触发条件中补上第二个不变式检查（即 OpenJDK mergeCollapse 的条件 2），三处同构修改：

stdlib/libs/std/sort/stable_sort.cj · maybeMerge()（:103 Comparable 版 / :493 comparator 版）
stdlib/libs/std/collection/array_list.cj · 合并逻辑（:1235，ArrayList 版，变量名为 runLengths）
// ln1 = 栈顶 run（刚压入），ln = 第 2 个，l = 第 3 个，lengthArr[n-2] = 第 4 个
- if (l <= ln + ln1) {
+ if (l <= ln + ln1 || (n > 1 && lengthArr[n - 2] <= lengthArr[n - 1] + ln)) {
  • 第一项（原有）：l ≤ ln + ln1 —— i = n-1 层不变式的违反条件（OpenJDK 条件 1）。
  • 第二项（新增）：lengthArr[n-2] ≤ lengthArr[n-1] + ln —— i = n-2 层不变式的违反条件（OpenJDK 条件 2）。 正是动画 ④ 中旧代码漏掉的那一层。
  • n > 1：边界保护 —— 栈内不足 3 个 run 时该层不存在，跳过检查。

5.2 命中后的恢复机制

任一条件命中即进入合并分支：选择相邻两个较短的 run 合并（保持合并平衡），随后 index-- 使检查窗口下移一层，继续检查更深处 —— 逐层向下传播，直到整栈不变式恢复才退出循环：

压入新 run
   │
   ▼
检查 i=n-1 层（条件①）＋ i=n-2 层（条件②·新增）
   │ 任一命中
   ▼
合并相邻较短的一对 run ──→ index--（窗口下移一层）
   │                        │
   │ ←──── 继续检查 ─────────┘
   │ 两层都满足
   ▼
退出循环：栈上每一层都满足不变式 ✓

  • 只有不变式真正成立，"栈深 ≤ 1.44×log₂(n)" 的上界推导才有效，容量公式才是真上界。
要点：PR #1764 修正容量（治标），PR #1779 补全不变式（治本）。 只有合并不变式整栈成立，容量公式的上界才成立。

6为什么必须两个 PR 配套

"只修一个行不行"是评审中最常见的问题。以下数据说明：单独任何一个都不够。

只修公式（仅有 #1764）

  • "公式 1.5×log₂+8 是栈深上界"这一结论成立的前提，是"不变式整栈成立"；
  • 旧检查漏掉 i=n-2 层 → 合并制造的深层违规永久潜伏（随机模拟中 0.19% 的步骤违规）；
  • 特制数据可使栈深超过 1.44×log₂(n)，公式上界失效，只能依赖 growRunStack 扩容兜底。

结论：越界风险仍然存在。

只补不变式（仅有 #1779）

  • 不变式成立后栈深 ≤ 1.44×log₂(n)，但旧公式只分配约 1.0×log₂(n/mrl)+1：
  • n = 2,048：需要 8 层，旧公式只给 7；
  • n = 8,192：需要 11 层，旧公式只给 9。

结论：无需特制数据，常规规模的最坏栈型即可越界。

两者结合（#1764 + #1779）：不变式保证栈深有界（≤ 1.44×log₂n）→ 公式覆盖该上界并留余量（1.5×log₂n+8）→ 即使前两层都被突破，growRunStack 倍增扩容仍保证不越界。三层共同构成对 issue #250 的完整修复。

为什么三者的"容量公式"形式不同？

三者的数学根基相同——都以 logφ(n) ≈ 1.44·log₂n（Fibonacci 不变式）推导，上表"最大栈深来源"一行 代入的其实是同一个公式，差别只在代入的规模域上限，以及由此选择的容量给定方式：

实现数组规模域由此选择的包装形式
OpenJDK数组长度受 int 索引限制，≤ 2³¹ 全域上界有限（logφ(2³¹/32) ≈ 38），预计算成 4 档常数（5 / 10 / 24 / 49， 各档贴近理论值 +2~11），小数组档位兼顾省内存
Pythonlist 长度按 64 位平台寻址上限推导（至 2⁶⁴） 全域一个常数：85 = logφ(2⁶⁴/32)，不随规模分档
仓颉（修复后）size 为 Int64，至 2⁶³（理论最坏栈深约 83） 一行动态公式 Int64(1.5·log₂n)+8：任意规模都取"当前上界 + 余量"， 小规模不必按全域最坏分配（n=65 给 17 而非 ~90），也无需维护档位表

余量策略的差异：仓颉统一取 1.5 系数与 +8 常数（约恒定 +15 槽），比 OpenJDK 各档 （+2~11）更保守 —— 同规模对比（n = 2³¹）：仓颉 54 槽、OpenJDK 49 槽、Python 85 槽（全域常数）。 仓颉多出的几个槽绝对值不足 100 字节，换来的是代码单行、无查表、对任意 n 无条件成立的严格上界。

说明：修复后的实现与 OpenJDK / Python 采用相同的数学推导（Fibonacci 上界）和相同的检查语义（两层条件）； 差别是容量按 n 动态计算而非取静态常数，且余量更保守（1.5 > 1.44，+8）。

8.2 timsort 的来源与演进

timsort 最初为 Python 开发，后来进入 Java 与 Android。各实现同源，run 栈的容量与检查规则在各自的发展过程中 经历过与本次 issue #250 同类的修正：

时间事件与本修复的关系
1993 Peter McIlroy 发表 Optimistic Sorting and Information Theoretic Complexity（SODA'93）， 提出按输入已有顺序自适应的归并排序框架 timsort 的理论源头：算法利用数据中天然有序的段
2002 Tim Peters 为 CPython 实现 timsort（Python 2.3 起用于 list.sort）， 设计文档 listsort.txt 给出 run 栈不变式与栈深推导 本报告 §2 的不变式与 1.44×log₂n 上界即来自这一推导
2011 Java 7 将 timsort 引入 Arrays.sort（对象数组），Android 平台同步采用， 成为部署量最大的比较排序之一 Python / Java 中的对照实现（§8.1 对照表）
2015 de Gouw 等人用 KeY 形式化验证证明当时 OpenJDK / Android 的 mergeCollapse 不能维持不变式， 并构造出使 run 栈超出预分配容量、抛 ArrayIndexOutOfBoundsException 的输入 （JDK-8072909，数组规模 > 2³⁰） 与 issue #250 同类同根因：检查语义不完整 → 栈深失控 → 越界写。 OpenJDK 的修法同样是"扩容量 + 补检查"（最大档位 40 → 49）
2018 Auger / Jugé / Nicaud / Pivoteau 发表 On the Worst-Case Complexity of TimSort， 严格刻画其最坏复杂度与合并策略 对栈深上界与合并策略给出严格分析
后续 de Gouw 等在 Journal of Automated Reasoning 发表修正版 timsort 的形式化正确性证明 PR #1779 补全后的两层检查语义与被证明正确的结构一致

参考：de Gouw 等 OpenJDK's java.utils.Collection.sort() is broken（CAV 2015， Springer / CWI PDF）； JDK-8072909； Auger 等 On the Worst-Case Complexity of TimSort； Verifying OpenJDK's Sort Method for Generic Collections（J. Autom. Reason.）

issue #250 与 OpenJDK 2015 年发现的问题同类、同根因； 修复后，仓颉的容量推导与检查条件与 OpenJDK / Python 一致。

9.1 术语表

run数组中一段天然有序（升序，或被反转的降序）的连续元素，排序的基本搬运单元。
minrun / mrl最短 run 长度（32~64，由数组规模决定）；不足的 run 会被二分插入补长。
run 栈排序过程中暂存待合并 run 的栈结构；容量在排序前预分配。
合并不变式len[i] > len[i+1] + len[i+2] —— 每个 run 严格长于其上两个之和，保证 Fibonacci 式递减。
maybeMerge仓颉实现中压栈后的合并检查函数，等价于标准 timSort 的 mergeCollapse。
治标 / 治本治标 = 修公式（使容量覆盖栈深上界）；治本 = 补不变式（使上界前提成立）。

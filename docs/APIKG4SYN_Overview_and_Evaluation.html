四步流水线
对应仓库里 construct_KG → generate_single/multi_api_data → eval 四个目录
1
解析文档

读取官方 API 声明文件（.d.ts），逐条提取类、方法、属性的名字与说明，整理成结构化清单（即“知识图谱”，存入 Neo4j 图数据库）。

2
出题 + 写答案

把清单喂给大模型：先按指定 API 出题（如“用 sort 和 removeByIndex 写一个排序并去尾的函数”），再让它写出答案代码；单 API 与多 API 两条线各自生成。

3
微调模型

用 8,000 条“题 → 答案”（6,400 单 API + 1,600 多 API）继续训练一个开源 7B 模型，让它学会按这种语言的 API 规范写代码。

4
验收

108 道人工题（每题带单元测试）交给模型作答，把代码放进真实工程编译、跑测试，统计通过率 pass@1。

APIKG4SYN 方法解读与评价6 / 11
代码核查：仓库现状（四个事实）
以下结论均可追溯至仓库代码
1
生成流程里没有校验环节

“编译不过就重写”的功能未接通：流程只负责出题、写码、落盘；单 API 生成器还引用了未定义的变量，本身跑不起来。

2
判对错只看“能否编译”

编译、测试日志中无报错即算对，不检查代码是否真的实现了题目要求（无行为验证、无断言）。

3
空答案样本不过滤

大模型输出解析失败时被记为空白并照常写入数据集（6,400 条中 34 条为空）。

4
重量级部分收益无证据

知识图谱 + 搜索选 API 组合（Neo4j + MCTS）环节复杂，但对最终效果的贡献没有直接的对照实验证据。

含义：以仓库代码现状，无法复现论文所述的生成流程；练习册里的“答案正确性”未经验证。
